# USPTO end-to-end reproduction

The source is [Zenodo record 16417648](https://zenodo.org/records/16417648),
*IR-NMR Multimodal Computational Spectra Dataset for 177K Patent-Extracted
Organic Molecules*. Only its nine `IR_data_chunk00*_of_009.parquet` shards are
used (177,461 spectra; approximately 8 GB). The protocol follows the molecular benchmarks and cross-validation
sections of the [UltraIR paper](https://arxiv.org/abs/2608.13341).

## Dataset provenance and citation

`USPTO` is the benchmark name used in this repository for the computational
IR spectra of patent-extracted molecules released by Federico Zipoli,
Marvin Alberts, and Teodoro Laino. The pipeline uses the nine IR shards
(177,461 molecules) from their IR–NMR dataset. The functional-group labels,
molecular properties and scaffold folds are generated by UltraIR's preparation
utilities.

- Dataset release: [Zenodo, DOI: 10.5281/zenodo.16417648](https://doi.org/10.5281/zenodo.16417648).
- Accompanying preprint: [IR–NMR Multimodal Computational Spectra Dataset for 177K Patent-Extracted Organic Molecules, DOI: 10.26434/chemrxiv-2025-l0zqz](https://doi.org/10.26434/chemrxiv-2025-l0zqz).

When reporting results using this benchmark, cite the accompanying preprint
as requested by the data authors, the dataset release, and the
[UltraIR paper](https://arxiv.org/abs/2608.13341) for the model and benchmark
protocol. The dataset release can be cited as:

```bibtex

  author    = {Zipoli, Federico and Alberts, Marvin and Laino, Teodoro},
  title     = {IR-NMR Multimodal Computational Spectra Dataset for 177K Patent-Extracted Organic Molecules},
```

## One command on a GPU machine

Run all commands from the UltraIR repository root. The full run stores data in
`data/uspto/` and training outputs in `runs/uspto/`. Smoke checks use
`data/uspto-smoke/` and `runs/uspto-smoke/`. Preparation examples in
the other data guides use `data/raw/` and `data/prepared/` for local inputs
and generated data. Input files must be obtained from the documented sources.

Install `curl` and the fixed runtime with Python 3.11; choose a CUDA PyTorch wheel suitable
for the driver before installing the remaining requirements:

```bash
python -m pip install -e .
# Run functional-group prediction across all five folds
python -m scripts.uspto_pipeline --work-dir runs/uspto --tasks fg
# Run all five USPTO tasks across all five folds
python -m scripts.uspto_pipeline --work-dir runs/uspto
```

The pipeline downloads and checksum-verifies all nine shards, crops and
normalizes spectra, generates molecular labels, creates five scaffold folds,
reuses or downloads the two encoder checkpoints in `checkpoints/pretraining/`,
trains the five USPTO tasks, reloads
the selected checkpoints for evaluation, exports example unlabeled predictions,
and writes the cross-validation summaries. The default uses the existing USPTO
YAML models and epoch counts: 100 epochs for the three molecular tasks and 20
for the two pair tasks, across all five folds.

Use a working volume with at least 130 GB free for all tasks. Pair arrays are
written with bounded RAM and removed after each fold unless `--keep-pairs` is
set. Use `--pair-dir /tmp/ultrair-uspto-pairs` to keep these
regenerable arrays on node-local storage; the selected mixture predictions and
metrics go to the run directory. On filesystems that do not support memory mapping, set `TMPDIR` to a local
scratch volume with at least 50 GB free; array writers stage there before
publishing the output files. Sixteen CPU cores and 64 GB RAM are a practical
starting allocation. GPU memory depends on the chosen batch size and task;
`--batch-size` can override the YAML value.

## Progress and estimated time remaining

The terminal displays the current stage (`DOWNLOAD`, `PREPARE`, or `RUN`).
Downloads show shard counts and curl's transfer progress and remaining time.
Spectral conversion and molecular label generation show molecule counts,
percentages, processing rates and ETA. Scaffold export shows completed folds
and an ETA based on elapsed export time.

During a run, each task and fold is identified before mixture preparation,
training, checkpoint-reload evaluation and example prediction. Training shows
epoch/batch progress and a training ETA after each completed epoch. Evaluation
and prediction show batch progress and ETA. Child-process output is streamed
to the terminal and saved in the per-fold log.

The overall run display counts completed task-folds (5 for `--tasks fg`,
25 for all tasks). Its remaining-time estimate uses completed folds of each
selected task and displays `estimating` until each unfinished task has a
measured fold duration. These estimates reflect processing rates and elapsed
time; they update as the run proceeds.

## Short end-to-end verification

```bash
python -m scripts.uspto_pipeline --work-dir runs/uspto-smoke --smoke
```

`--smoke` uses the first 256 real source molecules, one epoch and fold 1, with
a batch size of eight (one complete reference group for the pair sampler). All five tasks use their full model architectures and
released pretraining weights. Structure decoding is shortened to 16 tokens
and two beams/candidates. This provides a quick execution check. Full benchmark training uses
`runs/uspto/` with the default epoch counts and decoding settings.

For a single task or a subset of folds:

```bash
python -m scripts.uspto_pipeline \
  --work-dir runs/uspto-fg \
  --tasks fg --folds 1 2 3 4 5
```

Task names are `fg`, `properties`, `structure`, `detection`, and `fraction`.
`--epochs` is an explicit duration override for debugging or pilot runs.

## Separate preparation from GPU execution

Each stage can be run explicitly with the same work directory:

```bash
python -m scripts.uspto_pipeline --work-dir runs/uspto --stage download
python -m scripts.uspto_pipeline --work-dir runs/uspto --stage prepare
# Training and evaluation use the local GPU.
python -m scripts.uspto_pipeline --work-dir runs/uspto --stage run
```

`download` retrieves and verifies the public shards and encoder weights;
`prepare` builds aligned labels and scaffold folds; `run` trains, tests and
exports predictions. The run stage needs no public data download.

To continue a run after stopping it, add `--reuse-completed` with the same
work directory and settings. Finished folds are reused; an interrupted fold
starts training from its pretrained encoder again.

## Reuse existing inputs

`--data-dir` selects the dataset cache independently of `--work-dir`,
so multiple runs can share prepared inputs. Smoke checks use a separate
data directory automatically.

Pretrained encoders are stored in the repository's `checkpoints/pretraining/`
by default, matching the checkpoint download commands in the main README.
Existing encoder files are reused; missing files are downloaded there.
Use `--checkpoint-dir` to select a different location.

```bash
python -m scripts.uspto_pipeline \
  --raw-dir data/uspto/raw \
  --checkpoint-dir checkpoints/pretraining \
  --work-dir runs/uspto-rebuild
```

A supplied raw directory is treated as an existing input cache: all nine
shards must exist and match the published size and MD5. The source manifest
is written to the data directory. Supplied epoch-5 checkpoints are read in
place. Missing encoder files are downloaded into `--checkpoint-dir`.

Preparation builds aligned molecular arrays and scaffold folds from the
verified raw shards. Molecular structure prediction uses the formula-conditioned
generative adapter.

## Data and evaluation protocol

- Preserve shard order and row alignment, ID, SMILES, spectrum, labels, and
  original source-row indices. Invalid SMILES are removed together with their
  spectra and labels.
- Crop the original axis to 400–4000 cm⁻¹. For compatibility with the existing
  USPTO preparation, interpolate between the actual first/last retained source
  points (approximately 400.31696 and 3999.8335 cm⁻¹) to 3,600 samples and apply
  per-spectrum min-max normalization. The model resizes to 1,792 points using
  the repository's legacy cubic resize path.
- Generate the existing ordered 17 functional groups, 2,048-bit radius-two
  Morgan fingerprints, molecular formulas and 11 RDKit properties. Pin RDKit
  to **2025.03.6**: RDKit 2026 changes hydrogen-bond acceptor counts and therefore
  changes the property labels. Pin NumPy and OpenCV as well as the training
  dependencies in `requirements.txt`.
- Use one deterministic scaffold split for all tasks: five disjoint test
  folds, approximately 70/10/20 training/validation/test, seed 42. Non-empty
  Bemis–Murcko scaffolds remain intact and are checked for overlap in every
  fold. As in the repository splitter, molecules without a scaffold are
  assigned individually. Very large scaffold groups can make ratios differ
  from the target; the actual counts are recorded.
- Generate positive/negative mixtures independently **inside each split**.
  Each reference has four positive and four negative samples, with the same
  coefficient/noise recipe as `data.common.pairs`. All mixture components are drawn from the corresponding
  training, validation, or test subset.
- Property statistics are fitted on each fold's training subset by the existing
  task implementation. Functional-group thresholds use validation data only.
  Checkpoint selection and threshold calibration use validation data.

## Outputs

```text
data/uspto/                  # default data-dir
  source.json                # shard URLs, sizes and checksums
  raw/                       # downloaded Parquet shards
  converted/                 # aligned normalized spectra
  prepared/full/             # molecular arrays and labels
  prepared/fold-{1..5}/       # scaffold train/valid/test splits
  prepared/complete.json     # preparation settings and split audit
  pairs/fold-{1..5}/          # temporary mixture arrays
checkpoints/pretraining/     # shared pretrained encoders
runs/uspto/                  # default work-dir
  invocation.json            # command settings
  configs/<task>/fold-N.yaml  # effective per-fold configurations
  checkpoints/<task>/...     # trained best/last weights
  logs/                      # training and evaluation logs
  results/<task>/...         # metrics, predictions and summaries
  run_summary.json           # completed tasks/folds and elapsed times
```

Downloaded files are published after integrity checks; partial downloads can
be resumed. Completed matching preparation is reused. Preparation settings
(including the RDKit version) must match; use a new `--data-dir` when they
change. Training starts fresh by default. With `--reuse-completed`, a task/fold
is skipped only when its effective settings match and its selected checkpoint,
evaluation report and example prediction exist. Changed training settings
are rejected. This reuses finished folds; it does not resume a partially
trained epoch.

## Validation

See [VALIDATION.md](VALIDATION.md) for data checks, GPU execution checks and
full-data benchmark results. Effective per-fold configurations are saved under
`work-dir/configs/`, using the task YAML settings with resolved data paths,
output paths and device. CLI options such as `--epochs` and `--batch-size`
control the corresponding runtime settings.
